## 🖐 5 Hands-On Exercises — Platform Engineering Use Cases

### 1. Extracting a Field from a Kubernetes Manifest

**Scenario:** You've received a Deployment manifest and need to pull out the container image tag to confirm exactly what's currently deployed before deciding on a rollback.

```python
import yaml

# A Deployment manifest saved as a YAML string (normally read from a file)
manifest_yaml = """
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: payments-api
        image: registry.example.com/payments-api:2.4.1
"""

manifest = yaml.safe_load(manifest_yaml)

# Drill down to the field we care about before triggering a rollback
image = manifest["spec"]["template"]["spec"]["containers"][0]["image"]
print(image)  # registry.example.com/payments-api:2.4.1
```

**Why it matters:** Manifests are deeply nested, and pulling a single field programmatically (instead of eyeballing `kubectl get -o yaml` output) is the basis of any rollback script, drift checker, or deploy-verification step in a pipeline.

### 2. Summarizing a Terraform Plan JSON

**Scenario:** A `terraform show -json` plan was saved to disk, and you need to count how many resources will be created, updated, or destroyed so you can post a quick summary on the pull request.

```python
import json

# A `terraform show -json` plan, trimmed down to the relevant part
plan_json = """
{
  "resource_changes": [
    {"address": "aws_instance.web", "change": {"actions": ["create"]}},
    {"address": "aws_s3_bucket.logs", "change": {"actions": ["update"]}},
    {"address": "aws_security_group.old", "change": {"actions": ["delete"]}},
    {"address": "aws_instance.api", "change": {"actions": ["create"]}}
  ]
}
"""

plan = json.loads(plan_json)

# Tally planned actions for a quick PR summary
summary = {}
for resource in plan["resource_changes"]:
    for action in resource["change"]["actions"]:
        summary[action] = summary.get(action, 0) + 1

print(summary)  # {'create': 2, 'update': 1, 'delete': 1}
```

**Why it matters:** Reviewers rarely want to read a raw plan file — turning it into a small dict summary is what powers "2 to create, 1 to update, 1 to destroy" comments that make infrastructure changes easy to review at a glance.

### 3. Validating a JSON Config Against Required Keys

**Scenario:** Before a service deploys, CI should fail fast if its `config.json` is missing required keys like `name`, `replicas`, or `image`, rather than letting a broken config reach production.

```python
import json

def validate_config(config, required_keys):
    """Raise if any required key is missing from the config."""
    missing = required_keys - config.keys()
    if missing:
        raise ValueError(f"Config is missing required keys: {missing}")
    return True

required_keys = {"name", "replicas", "image"}

# A service config loaded from disk (represented inline here)
good_config = json.loads('{"name": "payments-api", "replicas": 3, "image": "payments-api:2.4.1"}')
bad_config = json.loads('{"name": "payments-api", "replicas": 3}')

for label, cfg in [("good_config", good_config), ("bad_config", bad_config)]:
    try:
        validate_config(cfg, required_keys)
        print(f"{label}: valid")
    except ValueError as e:
        print(f"{label}: {e}")

# Output:
# good_config: valid
# bad_config: Config is missing required keys: {'image'}
```

**Why it matters:** A missing key in a deploy config is the kind of bug that's cheap to catch in CI and expensive to debug in production — this pattern is the basis of a pre-deploy validation gate.

### 4. Writing a Python Dict to a YAML Config File

**Scenario:** You need to generate a Kubernetes ConfigMap from a Python dict of environment variables as part of a deploy script, instead of hand-editing YAML.

```python
import yaml

# Environment variables to inject into a Kubernetes ConfigMap
config_map = {
    "apiVersion": "v1",
    "kind": "ConfigMap",
    "metadata": {"name": "payments-api-config"},
    "data": {
        "LOG_LEVEL": "info",
        "MAX_CONNECTIONS": "50",
        "FEATURE_FLAG_NEW_CHECKOUT": "true"
    }
}

with open('configmap.yaml', 'w') as f:
    yaml.dump(config_map, f, default_flow_style=False, sort_keys=False)

# Output written to configmap.yaml:
# apiVersion: v1
# kind: ConfigMap
# metadata:
#   name: payments-api-config
# data:
#   LOG_LEVEL: info
#   MAX_CONNECTIONS: '50'
#   FEATURE_FLAG_NEW_CHECKOUT: 'true'
```

**Why it matters:** Generating manifests from Python dicts (rather than string-templating YAML by hand) avoids indentation bugs and lets you build ConfigMaps, Deployments, and Services programmatically from the same data your deploy script already has.

### 5. Merging Two JSON Config Files

**Scenario:** You have a base cloud config shared by every environment and a `production.json` override file, and you need one effective config where the override values win.

```python
import json

# Base config shared across all environments
base_config = {
    "app_name": "payments-api",
    "log_level": "warning",
    "timeout_seconds": 30,
    "retries": 3
}

# Environment-specific overrides
prod_overrides = {
    "log_level": "error",
    "timeout_seconds": 10
}

# Shallow merge: override values win over base values
merged_config = {**base_config, **prod_overrides}

with open('effective_config.json', 'w') as f:
    json.dump(merged_config, f, indent=2)

print(merged_config)
# {'app_name': 'payments-api', 'log_level': 'error', 'timeout_seconds': 10, 'retries': 3}
```

**Why it matters:** Layering a base config with environment-specific overrides is how most real deploy pipelines assemble their final settings — knowing how to merge dicts correctly (and when a shallow merge isn't enough) prevents subtle config bugs between environments.

### **1.3 Advanced JSON Handling**
```python
# Custom JSON encoder (for datetime objects)
from datetime import datetime
class CustomEncoder(json.JSONEncoder):
    def default(self, obj):
        if isinstance(obj, datetime):
            return obj.isoformat()
        return super().default(obj)

# Usage
cooking_log = {
    "timestamp": datetime.now(),
    "status": "done"
}

json_str = json.dumps(cooking_log, cls=CustomEncoder)
```

## **3. Real-World Configuration Examples**

### **3.1 Configuration Management**
```python
def load_config(config_path):
    """Load JSON or YAML config based on file extension"""
    if config_path.endswith('.json'):
        with open(config_path, 'r') as f:
            return json.load(f)
    elif config_path.endswith(('.yaml', '.yml')):
        with open(config_path, 'r') as f:
            return yaml.safe_load(f)
    else:
        raise ValueError("Unsupported config file format")

# Usage
recipe_settings = load_config('recipe.yaml')
pantry_settings = load_config('pantry.json')
```

### **3.2 Dynamic Template Generation**
```python
def generate_recipe_card(template_name, params):
    """Create a recipe card from a Jinja2 + YAML template"""
    from jinja2 import Template
    
    with open(f'templates/{template_name}.yaml.j2', 'r') as f:
        template = Template(f.read())
    
    rendered = template.render(params)
    return yaml.safe_load(rendered)

# Usage
pizza_card = generate_recipe_card(
    'pizza_template',
    {"servings": 6, "crust": "thin"}
)
```

### **3.3 Secret Management**
```python
import base64
from cryptography.fernet import Fernet

def decrypt_config(encrypted_file, key_file):
    """Decrypt a sensitive config file using a local Fernet key"""
    with open(key_file, 'rb') as kf:
        key = kf.read()
    fernet = Fernet(key)
    
    with open(encrypted_file, 'rb') as f:
        encrypted_data = f.read()
    
    # Decrypt with the Fernet key
    decrypted = fernet.decrypt(
        base64.b64decode(encrypted_data)
    )
    
    return yaml.safe_load(decrypted.decode('utf-8'))

# Usage
secret_recipe = decrypt_config('encrypted_recipe.yaml', 'secret.key')
```

## **4. Advanced Techniques**

### **4.1 JSON Schema Validation**
```python
from jsonschema import validate

schema = {
    "type": "object",
    "properties": {
        "name": {"type": "string"},
        "servings": {"type": "number", "minimum": 1},
        "tags": {"type": "array"}
    },
    "required": ["name"]
}

config = {
    "name": "Margherita Pizza",
    "servings": 4,
    "tags": ["vegetarian", "italian"]
}

try:
    validate(instance=config, schema=schema)
except Exception as e:
    print(f"Invalid config: {e}")
```

## **5. Best Practices for Configuration Files**

1. **Always use `safe_load` for YAML** - Prevents arbitrary code execution
2. **Validate configurations** with JSON Schema or similar
3. **Handle encoding explicitly** - Use `utf-8` unless specific requirements
4. **Use templates** (Jinja2) for dynamic configurations
5. **Secure sensitive data** - Never commit unencrypted secrets
6. **Version control configurations** - Track changes in Git
7. **Implement error handling** for malformed files:
   ```python
   try:
       config = yaml.safe_load(config_file)
   except yaml.YAMLError as e:
       print(f"Error parsing YAML: {e}")
   ```

| **Feature**       | **JSON**                      | **YAML**                      |
