### 1. Multi-Tier Alert Severity Routing

**Scenario:** A monitoring pipeline receives alerts from a system like Prometheus or CloudWatch and must route each one to the right channel — paging on-call for critical issues, posting to Slack for warnings during business hours, and just logging everything else.

```python
from datetime import datetime

def page_oncall(alert):
    print(f"Paging on-call for: {alert['message']}")

def post_to_slack(channel, alert):
    print(f"Posted to {channel}: {alert['message']}")

def log_alert(alert):
    print(f"Logged: {alert['message']}")

def route_alert(alert, hour=None):
    """Route an incoming monitoring alert based on severity and time of day."""
    severity = alert["severity"]          # 'critical', 'warning', or 'info'
    hour = hour if hour is not None else datetime.now().hour

    if severity == "critical":
        page_oncall(alert)                # Always wake someone up
        post_to_slack("#incidents", alert)
    elif severity == "warning" and (hour < 8 or hour >= 20):
        # Warnings outside business hours just get logged, not paged
        log_alert(alert)
    elif severity == "warning":
        post_to_slack("#alerts", alert)
    else:  # 'info' or anything else
        log_alert(alert)

# Example alert coming from a monitoring system, simulated at 2 AM
sample_alert = {"severity": "warning", "service": "checkout-api", "message": "Latency p99 above 800ms"}
route_alert(sample_alert, hour=2)
# Output: Logged: Latency p99 above 800ms
# (a 'warning' at 2 AM is outside business hours, so it's logged instead of paging anyone)
```

**Why it matters:** Routing alerts by severity and time keeps on-call engineers focused on what truly needs a human right now, cutting alert fatigue without dropping anything important.

### 2. Environment-Based Config Branching

**Scenario:** A deployment script needs different configuration — replica count, log verbosity, database host — depending on whether it's running in dev, staging, or production.

```python
def get_config(env):
    """Return environment-specific configuration for the app."""
    if env == "prod":
        return {"replicas": 6, "log_level": "WARNING", "db_host": "prod-db.internal"}
    elif env == "staging":
        return {"replicas": 2, "log_level": "INFO", "db_host": "staging-db.internal"}
    elif env == "dev":
        return {"replicas": 1, "log_level": "DEBUG", "db_host": "localhost"}
    else:
        raise ValueError(f"Unknown environment: {env}")

for environment in ["dev", "staging", "prod"]:
    config = get_config(environment)
    print(f"{environment}: replicas={config['replicas']}, log_level={config['log_level']}")

# Output:
# dev: replicas=1, log_level=DEBUG
# staging: replicas=2, log_level=INFO
# prod: replicas=6, log_level=WARNING
```

**Why it matters:** Branching config by environment from one script (instead of maintaining separate copies) keeps dev, staging, and prod consistent and avoids configuration drift.

### 3. Deploy-Approval Gate with Multiple Conditions

**Scenario:** A CI/CD pipeline should only allow a production deploy when tests pass, coverage is high enough, there are no critical vulnerabilities, and it isn't a Friday-afternoon freeze window.

```python
from datetime import datetime

def can_deploy(tests_passed, coverage, critical_vulns, now=None):
    """Decide whether a build is allowed to deploy to production."""
    now = now or datetime.now()
    is_friday_afternoon = now.weekday() == 4 and now.hour >= 14  # Friday freeze window

    if not tests_passed:
        return False, "Unit tests failed"
    if coverage < 80:
        return False, f"Coverage too low ({coverage}% < 80%)"
    if critical_vulns > 0:
        return False, f"{critical_vulns} critical vulnerabilities found"
    if is_friday_afternoon:
        return False, "Friday afternoon deploy freeze"
    return True, "All checks passed"

allowed, reason = can_deploy(tests_passed=True, coverage=87, critical_vulns=0,
                              now=datetime(2026, 8, 14, 10, 0))  # a Friday at 10 AM
print(f"Deploy allowed: {allowed} ({reason})")
# Output: Deploy allowed: True (All checks passed)
# (10 AM is before the 2 PM Friday freeze cutoff, so the deploy is allowed)
```

**Why it matters:** Stacking guard clauses for each release criterion makes the approval logic easy to read top-to-bottom and easy to extend when a new gate (e.g. change-freeze calendar) shows up later.

### 4. Ternary for Quick Status Labeling

**Scenario:** A Kubernetes pod status dashboard needs a one-line health label per pod — "OK" or "ATTENTION" — computed inline while building the display list.

```python
pods = [
    {"name": "api-7f9c", "restarts": 0, "ready": True},
    {"name": "worker-2b1a", "restarts": 5, "ready": False},
    {"name": "cache-9d3e", "restarts": 1, "ready": True},
]

# Ternary inside a comprehension: one line per pod, no if/else block needed
labels = [f"{p['name']}: {'OK' if p['ready'] and p['restarts'] < 3 else 'ATTENTION'}" for p in pods]

for label in labels:
    print(label)

# Output:
# api-7f9c: OK
# worker-2b1a: ATTENTION
# cache-9d3e: OK
```

**Why it matters:** A ternary keeps simple pass/fail labeling compact and readable, which is exactly the kind of one-shot decision that doesn't deserve a full if/else block.

### 5. Nested Conditions for a Rollout Health Check

**Scenario:** After a canary rollout, a script checks nested conditions — was the canary deployed, is the error rate acceptable, is latency acceptable — to decide whether to promote, hold, or roll back the release.

```python
def rollout_decision(canary_deployed, error_rate, p99_latency_ms):
    """Decide whether to promote, hold, or roll back a canary release."""
    if canary_deployed:
        if error_rate < 1.0:                 # error rate as a percentage
            if p99_latency_ms < 300:
                return "promote"
            else:
                return "hold"                # errors fine, but latency is borderline
        else:
            return "rollback"                # error rate too high, bail out
    else:
        return "hold"                        # canary never went live, nothing to evaluate

print(rollout_decision(canary_deployed=True, error_rate=0.4, p99_latency_ms=210))
print(rollout_decision(canary_deployed=True, error_rate=0.4, p99_latency_ms=450))
print(rollout_decision(canary_deployed=True, error_rate=2.1, p99_latency_ms=210))
print(rollout_decision(canary_deployed=False, error_rate=0.0, p99_latency_ms=0))

# Output:
# promote
# hold
# rollback
# hold
```

**Why it matters:** Nesting the checks in order of importance (deployed → errors → latency) mirrors how a human would triage a rollout, and each branch returns a single unambiguous decision.

## **1. Basic Conditional Statements**

### **if Statement**
The fundamental building block for decision-making:

```python
# Check if an order is ready to ship
order_status = get_order_status(order_id)['State']['Name']

if order_status == 'ready_to_ship':
    print(f"Order {order_id} is ready for dispatch")
    perform_quality_check(order_id)
```

### **if-else Statement**
Execute alternative code when condition fails:

```python
# Verify product stock status
stock_status = get_stock_status(product_id)

if stock_status == 'in_stock':
    process_new_order()
else:
    send_alert(f"Product {product_id} out of stock")
    cancel_order()
```

### **if-elif-else Ladder**
Handle multiple exclusive conditions:

```python
# Discount decision based on cart total
cart_total = get_cart_total()

if cart_total > 200:
    apply_discount(20)  # 20% off for big orders
elif cart_total < 30:
    apply_discount(0)   # No discount for small orders
else:
    apply_discount(10)  # Standard discount
```

## **8. Configuration-Driven Conditionals**
Externalize logic from code:

```python
# Load rules from config
discount_rules = {
    'big_spender': {'metric': 'CartTotal', 'threshold': 200, 'action': 'apply_20_percent'},
    'small_order': {'metric': 'CartTotal', 'threshold': 30, 'action': 'apply_free_shipping'}
}

current_metrics = get_order_metrics()

for rule_name, rule in discount_rules.items():
    if current_metrics[rule['metric']] > rule['threshold']:
        execute_action(rule['action'])
```

## **9. Best Practices for Conditional Logic**

1. **Avoid Deep Nesting** (Use early returns)
   ```python
   def handle_order():
       if not is_payment_valid(): return False
       if not is_stock_available(): return False
       return ship_order()
   ```

2. **Use Guard Clauses**
   ```python
   def process_return():
       if not returns_enabled: return
       if not item_eligible(): raise EligibilityError
       execute_return()
   ```

3. **Document Complex Conditions**
   ```python
   # Only apply discount during sale hours AND when not out of stock
   if (9 <= current_hour < 17) and not out_of_stock:
   ```

4. **Extract Complex Conditions**
   ```python
   def should_apply_discount():
       return (cart_total > 100 
               and items_count > 3 
               and not is_already_discounted() 
               and not is_blackout_period())
   ```

5. **Use Constants for Thresholds**
