## 🖐 5 Hands-On Exercises for Platform Engineering

### 1. Threshold Comparisons for Scaling Decisions

**Scenario:** A platform engineer monitors a Kubernetes Deployment's average CPU utilization (as reported by `kubectl top` / the metrics-server) and must decide whether to scale the replica count up, down, or leave it unchanged.

```python
# Kubernetes-style horizontal scaling decision based on CPU utilization

cpu_utilization_percent = 87       # Reported by metrics-server
current_replicas = 4
min_replicas = 2
max_replicas = 10

scale_up_threshold = 80
scale_down_threshold = 30

if cpu_utilization_percent > scale_up_threshold and current_replicas < max_replicas:
    new_replicas = current_replicas + 1
    print(f"Scaling UP: {current_replicas} -> {new_replicas} replicas (CPU at {cpu_utilization_percent}%)")
elif cpu_utilization_percent < scale_down_threshold and current_replicas > min_replicas:
    new_replicas = current_replicas - 1
    print(f"Scaling DOWN: {current_replicas} -> {new_replicas} replicas (CPU at {cpu_utilization_percent}%)")
else:
    new_replicas = current_replicas
    print(f"No scaling needed. Staying at {current_replicas} replicas (CPU at {cpu_utilization_percent}%)")

# Output: Scaling UP: 4 -> 5 replicas (CPU at 87%)
```

**Why it matters:** Comparison operators are the backbone of every autoscaler — HPA, Karpenter, or a custom controller all boil down to `>` / `<` checks against a threshold, and getting the boundary conditions right prevents flapping between scale-up and scale-down.

### 2. Membership Checks Against Allowlists

**Scenario:** A CI/CD pipeline must block deployment promotions unless the target Git branch and the container registry hosting the image are both on an approved allowlist.

```python
# CI/CD promotion gate using membership operators

approved_branches = {"main", "release/1.4", "release/1.5"}
approved_registries = {"registry.internal.company.com", "ghcr.io/company"}

target_branch = "release/1.5"
image_registry = "registry.internal.company.com"
image_tag = "registry.internal.company.com/api-service:1.5.2"

branch_ok = target_branch in approved_branches
registry_ok = image_registry in approved_registries
untrusted_source = "docker.io/random-user" not in image_tag  # sanity check against public mirrors

if branch_ok and registry_ok and untrusted_source:
    print(f"Promoting {image_tag} to production")
else:
    print(f"Blocked: {image_tag} failed the allowlist check")

# Output: Promoting registry.internal.company.com/api-service:1.5.2 to production
```

**Why it matters:** `in` / `not in` checks are the simplest and most auditable way to enforce allowlists and denylists in pipelines, and they read almost like the security policy they're implementing.

### 3. Bitwise Flags for Permissions

**Scenario:** A platform team encodes Terraform Cloud workspace permissions (read, plan, apply, admin) as bit flags on a CI service account, and needs to verify a requested action is authorized before running `terraform apply`.

```python
# Bitwise permission flags for a Terraform CI service account

READ  = 0b0001   # 1
PLAN  = 0b0010   # 2
APPLY = 0b0100   # 4
ADMIN = 0b1000   # 8

# This CI service account can read, plan, and apply - but is not an admin
service_account_perms = READ | PLAN | APPLY   # 0b0111 -> 7

requested_action = APPLY

if service_account_perms & requested_action:
    print("Authorized: service account may run 'terraform apply'")
else:
    print("Denied: service account lacks the required permission")

# Check if the account is (incorrectly) allowed to modify admin settings
if service_account_perms & ADMIN:
    print("WARNING: service account has admin rights")
else:
    print("OK: service account has no admin rights")

# Output:
# Authorized: service account may run 'terraform apply'
# OK: service account has no admin rights
```

**Why it matters:** Bitwise flags let you pack many boolean permissions into a single integer, which is exactly how Unix file modes, IAM permission sets, and many RBAC systems represent access under the hood — understanding `&`, `|`, and `~` demystifies all of them.

### 4. Chained Boolean Conditions for a Health-Check Gate

**Scenario:** Before a deployment pipeline cuts traffic over to a new service version, it must verify that all pods are ready, the database migration finished, no active incident is open, and the error rate is within budget — combined into a single health-check gate.

```python
# Deployment traffic-cutover gate combining multiple health signals

pods_ready = 6
pods_desired = 6
migration_complete = True
active_incident = False
error_rate_percent = 0.4
error_rate_budget = 1.0

all_pods_ready = pods_ready == pods_desired
error_rate_ok = error_rate_percent < error_rate_budget

healthy_to_cutover = (
    all_pods_ready
    and migration_complete
    and not active_incident
    and error_rate_ok
)

if healthy_to_cutover:
    print("Health-check gate PASSED: cutting traffic to the new version")
else:
    print("Health-check gate FAILED: holding traffic on the old version")

# Output: Health-check gate PASSED: cutting traffic to the new version
```

**Why it matters:** Real health checks are rarely a single condition — chaining `and`/`or`/`not` with short-circuit evaluation lets you express a precise release gate that fails safe the moment any one signal is bad.

### 5. Modulo for Batching and Round-Robin Assignment

**Scenario:** A rolling deployment needs to spread 23 application pods across 4 worker nodes in round-robin fashion so the scheduling load is distributed evenly.

```python
# Round-robin pod-to-node assignment using the modulo operator

pod_names = [f"pod-{i}" for i in range(23)]
worker_nodes = ["node-a", "node-b", "node-c", "node-d"]

assignment = {}
for index, pod in enumerate(pod_names):
    node = worker_nodes[index % len(worker_nodes)]
    assignment.setdefault(node, []).append(pod)

for node, pods in assignment.items():
    print(f"{node}: {len(pods)} pods")

# Output:
# node-a: 6 pods
# node-b: 6 pods
# node-c: 6 pods
# node-d: 5 pods
```

**Why it matters:** The modulo operator is the simplest possible load balancer — round-robin scheduling, canary batch sizing, and shard assignment all lean on `%` to cycle evenly through a fixed pool of targets.

Operators in Python are special symbols that perform operations on variables and values. In everyday programming, especially when building something like a recipe app, operators are essential for:
- Ingredient and quantity checks
- Recipe state evaluations
- Cooking logic flows
- Recipe comparisons

## **1. Arithmetic Operators (For Recipe Calculations)**

Used for mathematical operations in ingredient scaling, cost calculations, and serving-size adjustments.

| Operator | Description | Example |
|----------|-------------|----------------|
| `+` | Addition | `total_items = pantry_items + shopping_list_items` |
| `-` | Subtraction | `remaining_flour = total_flour - used_flour` |
| `*` | Multiplication | `total_cost = ingredient_count * price_per_unit` |
| `/` | Division | `avg_prep_time = total_prep_time / recipe_count` |
| `%` | Modulus | `is_even_servings = servings % 2 == 0` |
| `**` | Exponentiation | `dough_volume = base_size ** rise_factor` |
| `//` | Floor Division | `full_trays = total_cookies // cookies_per_tray` |

```python
# Grocery Cost Calculation
apple_count = 10
price_per_apple = 0.5
total_cost = apple_count * price_per_apple
print(f"Total cost: ${total_cost:.2f}")
# Output: Total cost: $5.00

# Flour Stock Check
total_flour = 1024  # grams
used_flour = 768
if (total_flour - used_flour) < 256:
    print("Warning: Not enough flour for another batch")
```

## **2. Comparison Operators (For Recipe Checks)**

Critical for recipe state evaluation in conditionals and cooking-tracking systems.

| Operator | Description | Example |
|----------|-------------|----------------|
| `==` | Equal | `if oven_status == 'preheated'` |
| `!=` | Not equal | `if desired_servings != actual_servings` |
| `>` | Greater than | `if cooking_temp > 400` |
| `<` | Less than | `if prep_time_min < 15` |
| `>=` | Greater or equal | `if spice_level >= 8` |
| `<=` | Less or equal | `if guest_count <= max_seats` |

```python
# Serving Size Check
desired_servings = 5
current_servings = get_current_serving_count()

if current_servings != desired_servings:
    adjust_recipe_quantities(desired_servings)

# Oven Temperature Alert
oven_temperature = get_oven_reading()
if oven_temperature > 220:
    trigger_alert("Oven running too hot!")
```

## **3. Logical Operators (For Complex Conditions)**

Combine multiple conditions in recipe decision-making.

| Operator | Description | Example |
|----------|-------------|----------------|
| `and` | Both true | `if oven_hot and timer_done` |
| `or` | Either true | `if pantry_empty or fridge_empty` |
| `not` | Inverts boolean | `if not is_fasting_day` |

```python
# Cooking Safety Check
is_weekday = datetime.now().weekday() < 5
is_dinner_time = 17 <= datetime.now().hour < 20
is_test_run = False

if (is_weekday and is_dinner_time) or is_test_run:
    start_cooking()
else:
    print("Cooking skipped outside dinner hours")

# Backup Recipe Condition
main_recipe_available = check_ingredient_status('pasta')
backup_recipe_available = check_ingredient_status('rice')

if not main_recipe_available and backup_recipe_available:
    switch_to_backup_recipe()
```

## **4. Assignment Operators (For Recipe Management)**

Used in recipe updates and quantity tracking.

| Operator | Example | Equivalent | Use Case |
|----------|---------|------------|-----------------|
| `=` | `x = 5` | - | Set initial quantity |
| `+=` | `x += 3` | `x = x + 3` | Add more servings |
| `-=` | `x -= 2` | `x = x - 2` | Reduce portion count |
| `*=` | `x *= 1.5` | `x = x * 1.5` | Scale up a recipe |
| `/=` | `x /= 2` | `x = x / 2` | Halve a recipe |
| `%=` | `x %= 10` | `x = x % 10` | Wrap batch numbering |
| `**=` | `x **= 2` | `x = x ** 2` | Compound rise time |
| `//=` | `x //= 2` | `x = x // 2` | Integer division for portioning |

```python
# Recipe scaling adjustment
current_servings = 4
scaling_adjustment = 2

current_servings += scaling_adjustment  # Scale up
print(f"New serving count: {current_servings}")
# Output: New serving count: 6

# Batch cooking counter
successful_batches = 0
total_batches = 10

while successful_batches < total_batches:
    if cook_batch():
        successful_batches += 1
```

## **5. Bitwise Operators (For Flag-Based Operations)**

Less common in everyday scripts but useful for flag processing, such as dietary tags on a recipe.

| Operator | Description | Example |
|----------|-------------|----------------|
| `&` | AND | `matches = recipe_tags & required_tags` |
| `\|` | OR | `tags = default_tags \| custom_tags` |
| `^` | XOR | `toggle = current_flag ^ 1` |
| `~` | NOT | `inverted_tags = ~original_tags` |
| `<<` | Left shift | `double_batch = current_batch << 1` |
| `>>` | Right shift | `half_batch = current_batch >> 1` |

```python
# Recipe Dietary Tag Checking
recipe_tags = 0b1101  # Binary: 1101 (vegan, gluten-free, nut-free)
required_tags = 0b1010  # Binary: 1010 (gluten-free, nut-free)

if (recipe_tags & required_tags) == required_tags:
    print("Recipe meets all dietary requirements")
else:
    print("Recipe does not meet dietary requirements")

# Pantry Slot Calculation
shelf_mask = 0b11111111_11111111_11111111_00000000
free_slots = ~shelf_mask
print(f"Available slots: {free_slots & 0xFFFFFFFF}")
```

## **7. Identity Operators (For Object Comparison)**

Used to compare object identity (memory address) rather than value.

| Operator | Description | Example |
|----------|-------------|----------------|
| `is` | Same object | `if recipe is DEFAULT_RECIPE` |
| `is not` | Different object | `if new_recipe is not old_recipe` |

```python
# Recipe Change Detection
current_recipe = get_saved_recipe()
new_recipe = load_recipe_file()

if new_recipe is not current_recipe:
    apply_recipe_changes(new_recipe)

# Singleton Pattern Check
class RecipeBook:
    _instance = None
    
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

book1 = RecipeBook()
book2 = RecipeBook()
print(book1 is book2)  # Output: True
```

## **8. Operator Precedence in Scripts**

Understanding execution order is crucial for complex conditions:

1. `()` (Parentheses)
2. `**` (Exponentiation)
3. `+x`, `-x`, `~x` (Unary operators)
4. `*`, `/`, `//`, `%`
5. `+`, `-`
6. `<<`, `>>`
7. `&`
8. `^`
9. `|`
10. `==`, `!=`, `>`, `<`, `>=`, `<=`, `is`, `is not`, `in`, `not in`
11. `not`
12. `and`
13. `or`

```python
# Complex Cooking Decision Example
oven_temp = 220
prep_time = 35
is_dinner_rush = True
is_kitchen_closed = False

if (oven_temp > 200 or prep_time > 30) and is_dinner_rush and not is_kitchen_closed:
    start_batch_cooking(2)
```

```python
# Recipe Type Selection
recipe_type = 'gourmet' if special_occasion else 'everyday'
```


## **10. Best Practices for Operators**

1. **Use parentheses** for complex expressions
2. **Leverage membership operators** for ingredient collections
3. **Prefer `is` vs `==`** when checking for `None`
4. **Use short-circuit evaluation** (`and`/`or`) wisely
5. **Document complex conditions** with comments
6. **Test edge cases** in recipe-scaling logic
7. **Use operator modules** for dynamic operations:

```python
import operator
ops = {
    'scale_up': operator.add,
    'scale_down': operator.sub
}
new_count = ops[action](current_count, adjustment)
```
