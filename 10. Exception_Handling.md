### 1. Retrying a Failed Cloud API Call

**Scenario:** You're polling a Kubernetes cluster's status API during a rollout, but the network is flaky right after a node restarts — the first couple of calls throw connection errors before the API becomes reachable again, so you need to retry with exponential backoff instead of failing immediately.

```python
import time
import requests

def call_cluster_api(url, attempt_state={"count": 0}):
    """
    Simulates calling a Kubernetes/cloud API endpoint.
    Fails with a ConnectionError on the first two attempts,
    then succeeds — mimicking a flaky network during a rollout.
    """
    attempt_state["count"] += 1
    if attempt_state["count"] < 3:
        raise requests.exceptions.ConnectionError("cluster API unreachable")
    return {"status": "healthy", "nodes": 3}

def get_cluster_status_with_retry(url, max_retries=5):
    for attempt in range(1, max_retries + 1):
        try:
            return call_cluster_api(url)
        except requests.exceptions.RequestException as e:
            print(f"Attempt {attempt} failed: {e}")
            if attempt == max_retries:
                raise
            wait = 2 ** attempt  # exponential backoff
            print(f"Retrying in {wait}s...")
            time.sleep(0.1)  # shortened for demo; real code would sleep(wait)
    raise RuntimeError("unreachable")

# Run it
status = get_cluster_status_with_retry("https://cluster.internal/api/v1/status")
print(f"Cluster status: {status}")
# Output:
# Attempt 1 failed: cluster API unreachable
# Retrying in 2s...
# Attempt 2 failed: cluster API unreachable
# Retrying in 4s...
# Cluster status: {'status': 'healthy', 'nodes': 3}
```

**Why it matters:** Transient network blips are the norm, not the exception, in distributed infrastructure — retrying with backoff turns a flaky dependency into a reliable call instead of paging someone at 3 a.m.

### 2. Validating a Kubernetes Deploy Config with a Custom Exception

**Scenario:** Before applying a deployment manifest, you want to validate it locally so a malformed config fails fast with a clear message instead of being rejected deep inside the cluster's API server.

```python
class ConfigValidationError(Exception):
    """Raised when a deployment config fails validation."""
    pass

def validate_deploy_config(config: dict):
    required_keys = ["image", "replicas", "namespace"]
    for key in required_keys:
        if key not in config:
            raise ConfigValidationError(f"Missing required field: '{key}'")

    if not isinstance(config["replicas"], int) or config["replicas"] < 1:
        raise ConfigValidationError(
            f"'replicas' must be a positive integer, got {config['replicas']!r}"
        )

    if "/" not in config["image"]:
        raise ConfigValidationError(
            f"'image' must include a registry path, got {config['image']!r}"
        )

    return True

# A deploy config missing 'namespace'
bad_config = {"image": "nginx", "replicas": 3}

try:
    validate_deploy_config(bad_config)
    print("Config is valid — proceeding with deployment")
except ConfigValidationError as e:
    print(f"Refusing to deploy: {e}")

# Output:
# Refusing to deploy: Missing required field: 'namespace'
```

**Why it matters:** A custom exception with a specific message turns "the deploy failed, good luck" into "here is exactly which field is wrong" — that difference is the gap between a two-second fix and a twenty-minute investigation.

### 3. Cleaning Up a Database Connection with finally

**Scenario:** A migration-check script opens a database connection to inspect the schema. Whether the check passes or an error interrupts it partway through, the connection must always be closed so it doesn't leak and exhaust the connection pool.

```python
import sqlite3

def run_migration_check(db_path):
    conn = None
    try:
        conn = sqlite3.connect(db_path)
        cursor = conn.cursor()
        cursor.execute("SELECT name FROM sqlite_master WHERE type='table'")
        tables = cursor.fetchall()
        print(f"Found {len(tables)} tables")
        # Simulate a failure partway through the migration check
        raise RuntimeError("schema drift detected")
    except RuntimeError as e:
        print(f"Migration check failed: {e}")
    finally:
        if conn is not None:
            conn.close()
            print("Database connection closed")  # always runs, leak avoided

run_migration_check(":memory:")

# Output:
# Found 0 tables
# Migration check failed: schema drift detected
# Database connection closed
```

**Why it matters:** `finally` guarantees cleanup runs no matter how the `try` block exits — in infrastructure code, an unclosed database connection, file handle, or SSH session is exactly the kind of leak that quietly exhausts resources in production.

### 4. Handling Different Failure Modes in a Deploy Script

**Scenario:** A deploy script can fail for very different reasons — a bad image tag versus a namespace over its pod quota — and each failure needs a different response, so you catch each exception type separately instead of lumping everything into one generic handler.

```python
class ImageNotFoundError(Exception):
    pass

class QuotaExceededError(Exception):
    pass

def push_and_deploy(image_tag, quota_used, quota_limit):
    if image_tag == "":
        raise ImageNotFoundError(f"image tag '{image_tag}' does not exist in registry")
    if quota_used >= quota_limit:
        raise QuotaExceededError(f"quota exceeded: {quota_used}/{quota_limit} pods used")
    return f"deployed {image_tag}"

deployments = [
    ("app:v1.2.0", 8, 10),
    ("", 3, 10),             # bad tag
    ("app:v1.3.0", 10, 10),  # over quota
]

for image_tag, used, limit in deployments:
    try:
        result = push_and_deploy(image_tag, used, limit)
        print(f"SUCCESS: {result}")
    except ImageNotFoundError as e:
        print(f"BUILD ERROR — fix the image tag: {e}")
    except QuotaExceededError as e:
        print(f"CAPACITY ERROR — request more quota: {e}")
    except Exception as e:
        print(f"UNEXPECTED ERROR: {e}")

# Output:
# SUCCESS: deployed app:v1.2.0
# BUILD ERROR — fix the image tag: image tag '' does not exist in registry
# CAPACITY ERROR — request more quota: quota exceeded: 10/10 pods used
```

**Why it matters:** A bad image tag needs a developer to push a new build; a quota problem needs an ops ticket for more capacity. Catching them separately routes each failure to the person and fix that actually resolve it, instead of one vague "deploy failed" alert.

### 5. A Health Check Using try, except, else

**Scenario:** A health-check sweep pings several internal services in turn. You want the "service is healthy" logic to run only when the ping genuinely succeeded — not accidentally trigger it inside the same block that might raise, which is exactly what `else` is for.

```python
def ping_service(service_name):
    """Simulates a health-check ping; deterministic for the demo."""
    if service_name == "payments-api":
        raise TimeoutError(f"{service_name} did not respond within 2s")
    return 200

def health_check(service_name):
    try:
        status_code = ping_service(service_name)
    except TimeoutError as e:
        print(f"UNHEALTHY: {service_name} — {e}")
    except Exception as e:
        print(f"UNKNOWN STATE: {service_name} — {e}")
    else:
        # Only runs when the try block raised nothing — the "happy path"
        print(f"HEALTHY: {service_name} responded with {status_code}")

for service in ["auth-api", "payments-api", "inventory-api"]:
    health_check(service)

# Output:
# HEALTHY: auth-api responded with 200
# UNHEALTHY: payments-api — payments-api did not respond within 2s
# HEALTHY: inventory-api responded with 200
```

**Why it matters:** Putting the success-path logic in `else` instead of at the bottom of `try` keeps you from accidentally catching an exception that success-path code itself might raise — the health check output only means "healthy" when the ping truly succeeded.

## **1. Basic Try-Except Structure**

### **Syntax**
```python
try:
    # Code that might raise exceptions
except ExceptionType:
    # Handle specific exception
except (ExceptionType1, ExceptionType2):
    # Handle multiple exceptions
except ExceptionType as e:
    # Access exception object
else:
    # Run if no exceptions
finally:
    # Always execute (cleanup)
```

### **1. Retry Mechanism**

```python
import time
from recipe_api.exceptions import RecipeAPIError

def fetch_recipe_with_retry(recipe_id, max_retries=3):
    attempt = 0
    while attempt < max_retries:
        try:
            return recipe_api.get_recipe(recipe_id)
        except RecipeAPIError as e:
            if e.error_code == 'RateLimitExceeded':
                attempt += 1
                time.sleep(2 ** attempt)  # Exponential backoff
            else:
                raise
    raise Exception(f"Failed after {max_retries} attempts")

# Usage
```

### **2. Context Manager for Resources**
```python
class SafeFileOpener:
    def __init__(self, filename, mode):
        self.filename = filename
        self.mode = mode
        
    def __enter__(self):
        try:
            self.file = open(self.filename, self.mode)
        except IOError as e:
            print(f"Failed to open {self.filename}: {e}")
            raise
        return self.file
        
    def __exit__(self, exc_type, exc_val, exc_tb):
        if self.file:
            self.file.close()
        if exc_type:
            print(f"Error occurred: {exc_val}")
        return True  # Suppress exception if needed

# Usage
try:

        recipe = yaml.safe_load(f)
```

```python
def add_recipe_to_menu(recipe_id, servings):
```

```python
import json
import os

def load_app_config(config_path):
    try:
        if not os.path.exists(config_path):
            raise FileNotFoundError(f"Config file {config_path} missing")
            
        with open(config_path, 'r') as f:
            try:
                return json.load(f)

        print(f"No permission to read {config_path}")

    except Exception as e:
        print(f"Unexpected error loading config: {e}")
```

## **5. Best Practices**

1. **Be specific with exceptions** - Catch only what you can handle
   ```python
   # Bad
   try:
       cook_recipe()
   except:
       pass
   
   # Good
   try:
       cook_recipe()
   except RecipeAPIError as e:
       handle_recipe_error(e)
   ```

2. **Implement retries with backoff** for transient failures
   ```python
   def retry_operation(func, max_retries=3, base_delay=1):
       for attempt in range(max_retries):
           try:
               return func()
           except TransientError as e:
               if attempt == max_retries - 1:
                   raise
               time.sleep(base_delay * (2 ** attempt))
   ```

3. **Log exceptions with context**
   ```python
   try:
       cook_meal()
   except Exception as e:
       logger.error(f"Meal prep failed. Recipe: {recipe_name}, Servings: {servings}", exc_info=True)
       raise
   ```

4. **Use custom exceptions** for business logic
   ```python
   class RecipeError(Exception):
       """Custom exception for recipe preparation failures"""
   
   try:
       validate_recipe()
   except ValidationError as e:
       raise RecipeError(f"Validation failed: {e}") from e
   ```

5. **Clean up resources in `finally`**
   ```python
   try:
       temp_file = create_temp_file()
       process_file(temp_file)
   finally:
       if os.path.exists(temp_file):
           os.unlink(temp_file)
   ```

6. **Chain exceptions properly** (Python 3+)
   ```python
   try:
       parse_recipe()
   except ValueError as e:
       raise RecipeFormatError("Invalid recipe format") from e
   ```

### **2. Timeout Handling**
```python
import signal

class TimeoutError(Exception):
    pass

def timeout_handler(signum, frame):
    raise TimeoutError("Operation timed out")

def run_with_timeout(func, timeout):
    signal.signal(signal.SIGALRM, timeout_handler)
    signal.alarm(timeout)
    try:
        result = func()
        signal.alarm(0)
        return result
    except TimeoutError:
        print("Timeout occurred")
        raise
    finally:
        signal.alarm(0)

# Usage
try:
    run_with_timeout(lambda: slow_baking_task(), 30)
except TimeoutError:
    notify_chef("Task timed out")
```

## **Conclusion**

Robust error handling enables developers to:
- **Build resilient applications** that survive temporary failures
- **Provide meaningful alerts** with diagnostic context
- **Implement safe fallbacks** when things go wrong
- **Maintain application stability** during partial failures
- **Debug issues faster** with proper logging

Key takeaways:
1. **Catch specific exceptions** - Avoid broad `except:` clauses
2. **Implement retry logic** for transient failures (network, rate limits)
3. **Use context managers** (`with`) for resource cleanup
4. **Log comprehensively** - Include relevant context
5. **Create custom exceptions** for business logic errors

This comprehensive approach to error handling will make your Python applications more reliable and maintainable in production.
