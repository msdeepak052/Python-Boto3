### 1. Import Styles for a Kubernetes Health-Check Script

**Scenario:** You're writing a script that polls the health of several Kubernetes-style services and want to see plain `import`, `import ... as`, and `from ... import` side by side in one realistic script.

```python
# health_check.py — comparing Python import styles in one script

import json                        # 1) standard "import module"
import statistics as stats         # 2) "import module as alias" — shorter name to type repeatedly
from datetime import date          # 3) "from module import name" — pull in just what you need

# from os import *                 # 4) "from module import *" — avoid this in real scripts,
                                    #    it dumps every name from os into this file's namespace

# Simulated results from polling several service health endpoints
service_status = {
    "auth-service": {"latency_ms": 42, "up": True},
    "billing-service": {"latency_ms": 118, "up": True},
    "queue-worker": {"latency_ms": 0, "up": False},
}

def check_services(status: dict) -> list:
    """Print each service's state and return the latencies of the healthy ones."""
    latencies = []
    for name, info in status.items():
        state = "UP" if info["up"] else "DOWN"
        print(f"{name}: {state} ({info['latency_ms']}ms)")
        if info["up"]:
            latencies.append(info["latency_ms"])
    return latencies

healthy_latencies = check_services(service_status)
print(f"Average latency of healthy services: {stats.mean(healthy_latencies):.1f}ms")
print(f"Health check run on: {date.today()}")
print(json.dumps(service_status, indent=2))  # raw status, ready to ship to a log pipeline

# Output:
# auth-service: UP (42ms)
# billing-service: UP (118ms)
# queue-worker: DOWN (0ms)
# Average latency of healthy services: 80.0ms
# Health check run on: <today's date>
# { ...json dump of service_status... }
```

**Why it matters:** Picking the right import style keeps health-check and monitoring scripts predictable — `import x as y` avoids typos on long names, `from x import y` keeps only what you use, and `from x import *` is avoided because it silently overwrites names and makes bugs in a production pipeline hard to trace.

### 2. Structuring a Terraform Wrapper as a Package with `__init__.py`

**Scenario:** You want other automation scripts to be able to run `from tf_wrapper import plan, apply` without knowing that `plan` and `apply` actually live in separate files — `__init__.py` is what makes that possible.

```python
# demo_tf_wrapper.py — build and use a small "tf_wrapper" package with __init__.py
import os
import sys
import tempfile

# 1) Create a temporary package directory: tf_wrapper/
pkg_dir = tempfile.mkdtemp()
tf_wrapper_path = os.path.join(pkg_dir, "tf_wrapper")
os.makedirs(tf_wrapper_path)

# 2) plan.py and apply.py hold the real logic, kept in separate small files
with open(os.path.join(tf_wrapper_path, "plan.py"), "w") as f:
    f.write(
        "def run_plan(environment):\n"
        "    return f'terraform plan -var-file={environment}.tfvars (dry run)'\n"
    )

with open(os.path.join(tf_wrapper_path, "apply.py"), "w") as f:
    f.write(
        "def run_apply(environment):\n"
        "    return f'terraform apply -var-file={environment}.tfvars (applied)'\n"
    )

# 3) __init__.py re-exports the two functions so callers never need to know
#    the internal file layout — they just do `from tf_wrapper import plan, apply`
with open(os.path.join(tf_wrapper_path, "__init__.py"), "w") as f:
    f.write(
        "from .plan import run_plan as plan\n"
        "from .apply import run_apply as apply\n"
    )

# 4) Make the temp dir importable, then use the package like any other
sys.path.insert(0, pkg_dir)
from tf_wrapper import plan, apply

print(plan("staging"))
print(apply("staging"))

# Output:
# terraform plan -var-file=staging.tfvars (dry run)
# terraform apply -var-file=staging.tfvars (applied)
```

**Why it matters:** `__init__.py` gives you a stable public import path (`tf_wrapper.plan`, `tf_wrapper.apply`) even if you later split, rename, or reorganize the files behind it — every CI/CD job that imports the wrapper keeps working unchanged.

### 3. Building a Reusable CI/CD Logging Utility Module

**Scenario:** Your `build`, `test`, and `deploy` pipeline stages each print status messages, and copy-pasting `print()` calls in every stage script has led to inconsistent formatting — you extract one shared logging module instead.

```python
# pipeline_logger.py — a reusable logging module shared by every CI/CD stage script
from datetime import datetime

def _timestamp():
    return datetime.now().strftime("%H:%M:%S")

def log_info(stage, msg):
    print(f"[{_timestamp()}] [INFO] [{stage}] {msg}")

def log_error(stage, msg):
    print(f"[{_timestamp()}] [ERROR] [{stage}] {msg}")


# --- build.py, test.py and deploy.py would each do: `import pipeline_logger as log` ---
# Simulated here as three stage functions calling the same shared module.

def build_stage():
    log_info("build", "Installing dependencies")
    log_info("build", "Build finished in 12s")

def test_stage():
    log_info("test", "Running unit tests")
    log_error("test", "2 tests failed")

def deploy_stage():
    log_info("deploy", "Rolling out new version")
    log_info("deploy", "Deploy complete")

build_stage()
test_stage()
deploy_stage()

# Output (timestamps will differ on your machine):
# [HH:MM:SS] [INFO] [build] Installing dependencies
# [HH:MM:SS] [INFO] [build] Build finished in 12s
# [HH:MM:SS] [INFO] [test] Running unit tests
# [HH:MM:SS] [ERROR] [test] 2 tests failed
# [HH:MM:SS] [INFO] [deploy] Rolling out new version
# [HH:MM:SS] [INFO] [deploy] Deploy complete
```

**Why it matters:** One shared module keeps log formatting identical across every pipeline stage, so log-parsing tools and dashboards can rely on a single predictable pattern instead of three slightly different ones hand-rolled per script.

### 4. Using `if __name__ == "__main__"` in a Deployable Automation Script

**Scenario:** A config-validation script needs to be importable by your test suite (so tests can call its functions directly) *and* runnable as a standalone step in a CI/CD job right before deployment.

```python
# validate_config.py — importable module AND a standalone CI/CD step

import json

REQUIRED_KEYS = {"service_name", "replicas", "image_tag"}

def validate_config(config: dict) -> list:
    """Return a list of problems found in a deployment config; empty list = valid."""
    problems = []
    missing = REQUIRED_KEYS - config.keys()
    if missing:
        problems.append(f"Missing keys: {sorted(missing)}")
    if "replicas" in config and config["replicas"] < 1:
        problems.append("replicas must be at least 1")
    return problems

def load_config(raw_json: str) -> dict:
    return json.loads(raw_json)

if __name__ == "__main__":
    # This block only runs when the file is executed directly,
    # e.g. `python validate_config.py` as a CI/CD pipeline step —
    # it is skipped when a test file does `import validate_config`.
    sample_config = '{"service_name": "billing-api", "replicas": 3, "image_tag": "v2.1.0"}'
    config = load_config(sample_config)
    issues = validate_config(config)

    if issues:
        print("Config INVALID:", issues)
        raise SystemExit(1)  # non-zero exit code fails the pipeline step
    else:
        print("Config VALID — proceeding with deployment")

# Output:
# Config VALID — proceeding with deployment
```

**Why it matters:** The `if __name__ == "__main__"` guard lets one file serve two jobs — a set of unit-testable functions, and a standalone script the pipeline can execute directly — without duplicating any code.

### 5. Managing Third-Party Packages with venv and pip for a Cloud API Client

**Scenario:** You need to poll a cloud provider's status API from a script. Before writing any code you isolate the project's dependencies in a `venv`, install the HTTP client library with `pip`, and pin the exact version for the CI/CD runner.

```bash
# 1) Create and activate an isolated environment for this automation script
python -m venv venv
source venv/bin/activate        # venv\Scripts\activate on Windows

# 2) Install only what this script needs
pip install requests

# 3) Freeze exact versions so the CI/CD runner installs the same ones
pip freeze > requirements.txt
```

```python
# cloud_status_client.py — polling a cloud provider's status API
# Third-party SDKs (requests, or an AWS/GCP-style client library such as boto3)
# generally follow the same pattern: create a client/session, call a method,
# then read fields off the structured response that comes back.
import requests

def get_service_status(api_url, service_name):
    """Call a cloud status API and return whether the service is operational."""
    response = requests.get(f"{api_url}/status/{service_name}", timeout=5)
    response.raise_for_status()          # raises if the API returned an error code
    data = response.json()
    return data.get("status", "unknown")

if __name__ == "__main__":
    # In real usage this hits a live endpoint; here we just show the call shape
    # so the script runs safely without needing network access or credentials.
    # status = get_service_status("https://status.example-cloud.com/api", "compute")
    # print(f"compute service status: {status}")
    print("Client ready — installed via pip inside an isolated venv")

# Output:
# Client ready — installed via pip inside an isolated venv
```

**Why it matters:** A dedicated `venv` plus a pinned `requirements.txt` means the exact same `requests` version runs on your laptop and in the CI/CD runner, so "it works on my machine" never becomes the reason a deployment step fails.

## 🧠 What is a Python Module?

A **module** is simply a **Python file (`.py`)** that contains **functions, variables, classes, or runnable code**.
It allows you to **organize code logically** and **reuse it** across multiple scripts or projects.

### ✅ Why Use Modules?

| Benefit               | Explanation                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| 🔁 Reusability        | Write once, use many times                                                                  |
| 📦 Organization       | Separate concerns into different files                                                      |
| 🛠️ Maintainability   | Easier to debug, update, and test                                                           |
| 🧪 Testability        | Functions in modules are easier to test                                                     |
| ♻️ Everyday Automation | You can create a module for recipe logic, one for pantry stock, one for meal logging, etc. |

## **2. How to Import Modules**
There are multiple ways to import modules:

### **1. Basic Import**
```python
import math
print(math.sqrt(16))  # Output: 4.0
```

### **2. Import with Alias**
```python
import math as m
print(m.sqrt(25))  # Output: 5.0
```

### **3. Import Specific Functions**
```python
from math import sqrt, pow
print(sqrt(36))  # Output: 6.0
print(pow(2, 3))  # Output: 8.0
```

### **4. Import All Functions (Not Recommended)**
```python
from math import *  # Imports all functions
print(sqrt(49))  # Output: 7.0
```
⚠️ **Warning:** This can lead to naming conflicts.

## 🗂️ Special Module Parameters

### `__name__`

This is a **built-in variable** in every Python module.

```python
# mymodule.py
print("Name is", __name__)
```

When run directly:

```bash
$ python mymodule.py
# Output: Name is __main__
```

When imported:

```python
import mymodule
# Output: Name is mymodule
```

✅ Use it to conditionally run code only when the module is the entry point.

```python
def test_func():
    print("Running test")

if __name__ == "__main__":
    test_func()  # Only runs when executed directly
```

## **3. Module Search Path**
When you import a module, Python searches in the following order:
1. **Current directory**
2. **PYTHONPATH** (environment variable)
3. **Standard library directories**
4. **Site-packages** (for third-party modules)

You can check the search path using:
```python
import sys
print(sys.path)
```

## **5. Special Module Variables**
When a module is imported, Python defines some special variables:

| Variable | Description | Example |
|----------|-------------|---------|
| `__name__` | Name of the module | `__name__ == "__main__"` when run directly |
| `__file__` | Path of the module | `print(__file__)` → `/path/to/module.py` |
| `__doc__` | Module docstring | `print(math.__doc__)` |

### **Example: `__name__` Usage**
```python
# File: `test_module.py`
def greet():
    print("Hello from module!")

if __name__ == "__main__":
    print("Running directly")
    greet()
else:
    print("Imported as a module")
```
- If run directly (`python test_module.py`), it prints:  
  ```
  Running directly
  Hello from module!
  ```
- If imported (`import test_module`), it prints:  
  ```
  Imported as a module
  ```

## **6. Organizing Modules into Packages**
A **package** is a collection of modules in a directory with `__init__.py`.

### **Example: Kitchen Package**
```
kitchen/
│
├── __init__.py          # Marks this as a package
├── oven_utils.py         # Oven-related functions
├── pantry_utils.py       # Pantry-related functions
```

## **8. Best Practices for Modules**
1. **Modularize kitchen operations** (e.g., `oven.py`, `pantry.py`).
2. **Use `__init__.py`** to define package-level imports.
3. **Avoid Circular Imports** (Module A imports Module B, which imports Module A).
4. **Document Modules** with docstrings.
5. **Use `if __name__ == "__main__"`** for testing.

## **9. Real-World Example: Kitchen Automation Module**
```python
# File: `kitchen_automation.py`

class KitchenManager:
    """Handles oven and pantry operations"""

    def __init__(self, kitchen_name='main-kitchen'):
        self.kitchen_name = kitchen_name
        self.pantry_items = []

    def start_oven(self, recipe_id):
        """Starts preheating the oven for a recipe"""
        print(f"Preheating oven in {self.kitchen_name} for recipe: {recipe_id}")

        self.pantry_items.append(item_path.split('/')[-1])

# Usage:

    kitchen.start_oven("recipe-042")
    kitchen.store_in_pantry("/data/flour.txt", "shelf-2")
```

## 🧠 What is a Package in Python?

A **package** is a **collection of related modules** (Python `.py` files) organized in **directories** with an `__init__.py` file.

> ✅ In simple terms:
> **Module = one file**
> **Package = folder containing modules + `__init__.py`**

## 🧠 What is `venv` in Python?

`venv` stands for **Virtual Environment**.

It is a **self-contained Python environment** that allows you to:

* Install packages **only for your project**
* Avoid **global conflicts**
* Maintain **project-specific versions** of libraries (like `requests`, `pillow`, etc.)
* Work safely on **multiple Python projects** on the same machine

---

## ✅ Why You Should Use `venv`

| Reason               | Benefit                                                                             |
| --------------------- | ------------------------------------------------------------------------------------- |
| 🧪 Isolation          | Keeps your project's dependencies separate from global packages                       |
| 🔁 Portability        | Easily share project using `requirements.txt`                                         |
| 🔐 Safe Testing       | Install tools like `requests`, `pytest`, `faker`, etc., without polluting system Python |
| 🛠 Automation Scripts | Consistent and reproducible environments                                              |

---

## 🔧 How to Create and Use `venv`

> Works for Python 3.3 and above.

### ✅ 1. Create a Virtual Environment

From your project folder:

```bash
python -m venv venv
```

* This creates a folder called `venv/`
* It contains a copy of Python and pip

---

### ✅ 2. Activate the Virtual Environment

| OS        | Command                    |
| --------- | --------------------------- |
| Windows   | `venv\Scripts\activate`    |
| Linux/Mac | `source venv/bin/activate` |

> After activation, your terminal will show `(venv)` prefix.

---

### ✅ 3. Install Packages Locally

```bash
pip install requests
pip install pillow
```

These are now installed **only inside `venv/`**.

---

### ✅ 4. Save Dependencies

```bash
pip freeze > requirements.txt
```

This creates a file like:

```txt
requests==2.31.0
pillow==10.2.0
```

Useful for:

* Team collaboration
* Reproducible builds
* Automated scripts

---

### ✅ 5. Load Environment Automatically in VS Code

VS Code will detect and suggest the environment, or you can manually:

* Press `Ctrl+Shift+P`
* Search: `Python: Select Interpreter`
* Choose: `./venv/bin/python` or `.\venv\Scripts\python.exe`

Then update `.vscode/settings.json`:

```json
{
  "python.pythonPath": "venv/Scripts/python.exe"
}
```

## 🧠 What is a Python Workspace?

A **workspace** in Python (especially in editors like **VS Code**) is a **folder or set of folders** that contains:

* Source code files (`.py`)
* Modules and packages
* Configuration files (`.env`, `.vscode/`, `.gitignore`, etc.)
* Virtual environments (`venv`)
* Dependencies (`requirements.txt` or `pyproject.toml`)
* External tools, linters, formatters, etc.

> Think of a workspace as a **project folder** for Python development.

---

## ✅ Why Are Workspaces Important?

| Benefit                     | Explanation                                                          |
| ---------------------------- | ------------------------------------------------------------------- |
| 📂 Organization             | Keeps related files/modules together                                |
| 🛠️ Tooling Integration     | Enables IntelliSense, linting, debugging                            |
| ⚙️ Environment Control      | Can isolate virtual environments per project                        |
| 🔁 Reusability & Modularity | Structure reusable automation scripts (e.g., recipe scripts, meal-planning logic) |
