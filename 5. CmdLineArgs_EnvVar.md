## 🖐 5 Hands-On Exercises — Platform Engineering Use Cases

### 1. Deploying to a Kubernetes Cluster with `argparse`

**Scenario:** You're writing a `deploy.py` script that your team runs from CI/CD against different Kubernetes clusters — it needs a required environment flag, an optional namespace with a default, a typed replica count, and a `--dry-run` switch so engineers can preview a rollout before it actually happens.

```python
# deploy.py
import argparse

def main():
    parser = argparse.ArgumentParser(
        description="Deploy the app to a Kubernetes cluster"
    )
    parser.add_argument("--env", required=True, choices=["dev", "staging", "prod"],
                         help="Target environment")
    parser.add_argument("--namespace", default="default",
                         help="Kubernetes namespace to deploy into")
    parser.add_argument("--replicas", type=int, default=2,
                         help="Number of pod replicas to run")
    parser.add_argument("--dry-run", action="store_true",
                         help="Print the plan without applying it")

    args = parser.parse_args()

    action = "Would deploy" if args.dry_run else "Deploying"
    print(f"{action} to {args.env} (namespace={args.namespace}, replicas={args.replicas})")

if __name__ == "__main__":
    main()
```

Run:

```bash
python deploy.py --env staging --namespace payments --replicas 4 --dry-run
```

Output:

```
Would deploy to staging (namespace=payments, replicas=4)
```

**Why it matters:** every deploy script eventually needs required flags, sane defaults, and a safe "preview" mode — `argparse` gives you all three with almost no boilerplate, instead of a pile of hand-rolled `if len(sys.argv) < 3` checks.

### 2. Reading Required vs Optional Environment Variables

**Scenario:** A Terraform wrapper script needs the cloud region to be optional (falling back to a sane default) but the remote state bucket to be required — the pipeline should fail fast with a clear message before `terraform init` ever runs, instead of failing deep inside Terraform's own error output.

```python
import os
import sys

def load_terraform_config():
    # Optional: falls back to a sensible default if not set
    region = os.environ.get("TF_VAR_region", "us-east-1")

    # Required: the pipeline must fail loudly, not silently, if this is missing
    state_bucket = os.environ.get("TF_STATE_BUCKET")
    if state_bucket is None:
        sys.exit("ERROR: TF_STATE_BUCKET is not set. Cannot initialize Terraform backend.")

    print(f"Using region: {region}")
    print(f"Using state bucket: {state_bucket}")
    return region, state_bucket

load_terraform_config()
```

Run (with `TF_STATE_BUCKET=my-tf-state` exported, `TF_VAR_region` left unset):

```
Using region: us-east-1
Using state bucket: my-tf-state
```

**Why it matters:** distinguishing "optional with a default" from "required, fail immediately" at the top of a script is what turns a cryptic mid-pipeline crash into a one-line, actionable error message.

### 3. Validating Environment Variable Types

**Scenario:** A CI/CD pipeline reads `MAX_RETRIES` and `ENABLE_CANARY` from the pipeline's environment to control rollout logic. Both arrive as strings, so the script must cast and validate them up front rather than letting a bad value silently break comparisons deep inside the deploy logic.

```python
import os

def get_int_env(name, default):
    raw = os.environ.get(name, str(default))
    try:
        return int(raw)
    except ValueError:
        raise ValueError(f"{name} must be an integer, got: {raw!r}")

def get_bool_env(name, default=False):
    raw = os.environ.get(name, str(default))
    return raw.strip().lower() in ("1", "true", "yes")

max_retries = get_int_env("MAX_RETRIES", 3)
enable_canary = get_bool_env("ENABLE_CANARY", False)

print(f"Max retries: {max_retries}")
print(f"Canary rollout enabled: {enable_canary}")
```

Run (with `MAX_RETRIES=5` and `ENABLE_CANARY=true` exported):

```
Max retries: 5
Canary rollout enabled: True
```

**Why it matters:** environment variables are always strings — validating and casting them at the boundary catches typos (`MAX_RETRIES=five`) with a clear error instead of a confusing `TypeError` three functions later.

### 4. Building a Small CLI Tool with Flags

**Scenario:** Platform engineers keep running a dozen ad hoc `kubectl` one-liners to check pod health across clusters. You replace that with a small internal tool, `podstatus.py`, that accepts a cluster context, a namespace, and a `--verbose` flag for extra debug output.

```python
# podstatus.py
import argparse

def check_pods(context, namespace, verbose):
    print(f"Checking pods in context={context}, namespace={namespace}")
    if verbose:
        print("  (verbose) connecting to API server, listing pod objects...")
    # Simulated result
    print("  3 pods running, 0 pending, 0 failed")

def main():
    parser = argparse.ArgumentParser(description="Check pod status across clusters")
    parser.add_argument("--context", default="default", help="kubeconfig context to use")
    parser.add_argument("--namespace", "-n", default="default", help="Namespace to inspect")
    parser.add_argument("--verbose", "-v", action="store_true", help="Show extra debug output")
    args = parser.parse_args()

    check_pods(args.context, args.namespace, args.verbose)

if __name__ == "__main__":
    main()
```

Run:

```bash
python podstatus.py --context prod-cluster -n payments -v
```

Output:

```
Checking pods in context=prod-cluster, namespace=payments
  (verbose) connecting to API server, listing pod objects...
  3 pods running, 0 pending, 0 failed
```

**Why it matters:** a five-minute `argparse` wrapper with short flags (`-n`, `-v`) and built-in `--help` turns a scattered pile of shell aliases into a tool the whole platform team can actually discover and use.

### 5. Combining CLI Overrides with Environment Variable Config

**Scenario:** In CI, secrets and the deploy region come from environment variables injected by the pipeline. When a developer runs the same script locally to test a fix, they want to override just the region via a CLI flag without exporting new environment variables — the classic "env vars set the baseline, CLI flags override it" layering used by real deploy tooling.

```python
import argparse
import os

def build_config():
    parser = argparse.ArgumentParser(description="Deploy with layered config")
    # No default here on purpose — the env var is the real default, CLI is the override
    parser.add_argument("--region", help="Override the deploy region")
    parser.add_argument("--api-key", help="Override the API key (rarely needed)")
    args = parser.parse_args()

    # Priority: CLI flag > environment variable > hardcoded fallback
    region = args.region or os.environ.get("DEPLOY_REGION", "us-east-1")
    api_key = args.api_key or os.environ.get("DEPLOY_API_KEY")

    if api_key is None:
        raise SystemExit("ERROR: No API key found in --api-key or DEPLOY_API_KEY.")

    print(f"Deploying using region={region}")
    return region, api_key

build_config()
```

Run (with `DEPLOY_API_KEY=abc123` and `DEPLOY_REGION=eu-west-1` exported, then overridden on the command line):

```bash
python deploy_layered.py --region ap-south-1
```

Output:

```
Deploying using region=ap-south-1
```

**Why it matters:** layering config this way — env vars for the pipeline's baseline, CLI flags for one-off local overrides — means the same script works unmodified in CI and on a developer's laptop.

## 🧠 What Are Command Line Arguments?

**Command line arguments** allow you to **pass values to your Python script at runtime**, directly from the terminal, without hardcoding them in the code.

For example:

```bash
python report.py 10A Math
```

* `"10A"` and `"Math"` are **command line arguments**.

---

## ✅ Why Are They Useful?

| Use Case                     | Description                                       |
| ----------------------------- | -------------------------------------------------- |
| 🔁 Reuse Scripts             | Run the same script for different classes or subjects |
| 🧪 Parametrize Tasks         | Pass class name, student ID, output format, etc.  |
| 🛠️ Automate Repetitive Jobs | Use CLI args in scheduled batch jobs               |
| 📦 Integrate with Tools      | Use arguments to feed data between scripts         |

---

## ✅ 3 Ways to Handle CLI Arguments in Python

| Method     | Description                                 |
| ---------- | -------------------------------------------- |
| `sys.argv` | Basic argument access                       |
| `argparse` | Recommended for structured CLI tools        |
| `click`    | External package for elegant CLI (optional) |

We'll focus on `sys.argv` and `argparse` — the two most useful for everyday scripts.

---

## ✅ 1. Using `sys.argv` (Basic & Fast)

### 🔧 Example

```python
# report.py
import sys

print("All args:", sys.argv)
print("Script name:", sys.argv[0])
print("Class:", sys.argv[1])
print("Subject:", sys.argv[2])
```

### ▶️ Run:

```bash
python report.py 10A Math
```

### ✅ Output:

```
All args: ['report.py', '10A', 'Math']
Script name: report.py
Class: 10A
Subject: Math
```

### ⚠️ Limitation:

* No type checking
* No help messages
* Manual error handling

---

## ✅ 2. Using `argparse` (Most Powerful & Recommended)

Python’s built-in module to create **user-friendly CLI tools**.

---

### ✅ Step-by-Step Example

```python
# generate_report.py
import argparse

parser = argparse.ArgumentParser(description="Generate a student report card")

# Add arguments
parser.add_argument("--class", dest="class_name", help="Class name", required=True)
parser.add_argument("--subject", help="Subject name", default="General")
parser.add_argument("--format", help="Report format", choices=["pdf", "csv"], default="pdf")

# Parse them
args = parser.parse_args()

print(f"Class: {args.class_name}")
print(f"Subject: {args.subject}")
print(f"Format: {args.format}")
```

### ▶️ Run:

```bash
python generate_report.py --class 10A --subject Math --format csv
```

### ✅ Output:

```
Class: 10A
Subject: Math
Format: csv
```

---

## 🔍 `argparse` Parameters Explained

| Parameter       | Description                                      |
| --------------- | ------------------------------------------------ |
| `help`          | Shown when user adds `-h` or `--help`            |
| `required=True` | Argument must be provided                        |
| `default=`      | Default value if not passed                      |
| `choices=[]`    | Restricts input to valid options                 |
| `type=`         | Convert input to type (int, str, float)          |
| `nargs=`        | Accepts multiple arguments (e.g., list of files) |

## ✅ **What are Environment Variables?**

Environment Variables are **key-value pairs maintained by the operating system**. They provide a way to **configure a program without hardcoding values** into the source code.

In Python, we typically interact with them using the **`os`** module, and they are widely used for:

* Managing **sensitive settings** (passwords, API keys, tokens)
* Defining **runtime configuration** (limits, modes, paths)
* Supporting the **"config lives outside the code"** principle
* Working with **scheduled scripts, automation tools, and shared computers**

---

## 📦 **Importing Required Module**

```python
import os
```

---

## 🧵 Accessing Environment Variables

### 1. `os.environ` – Mapping of Environment Variables

```python
print(os.environ)  # Returns all current environment variables as a mapping (dict-like)
```

### 2. Access Specific Variable

```python
teacher_name = os.environ['TEACHER_NAME']  # KeyError if not found
```

### 3. Safe Access (Preferred)

```python
admin_password = os.environ.get('ADMIN_PASSWORD', 'default_password')  # Returns default if not set
```

🔐 Use this so the program doesn't crash just because one environment variable is missing.

---

## 🔍 Setting Environment Variables

### A. Within Python Script (Temporary – for current process only)

```python
os.environ['SCHOOL_TERM'] = 'spring'
```

> ⚠️ This does **not persist** after the script ends.

### B. Using `export` in Linux/macOS or `set` in Windows

```bash
export TEACHER_NAME=admin  # Linux/macOS
set TEACHER_NAME=admin     # Windows
```

Or include it in a `.env` file and load using `python-dotenv`.

---

## 🧪 Example: Using Environment Variables in a Python Script

```python
import os

def open_gradebook():
    school_name = os.environ.get("SCHOOL_NAME", "Green Valley School")
    school_year = os.environ.get("SCHOOL_YEAR", "2026")
    teacher_name = os.environ.get("TEACHER_NAME", "admin")
    admin_password = os.environ.get("ADMIN_PASSWORD")

    if admin_password is None:
        raise EnvironmentError("ADMIN_PASSWORD is not set. Exiting for security.")

    print(f"Opening gradebook for {school_name} ({school_year}) as {teacher_name}")
    # Simulated gradebook access
    return True

open_gradebook()
```

**Sample .env File (used by automated scripts, or loaded manually):**

```env
SCHOOL_NAME=Green Valley School
SCHOOL_YEAR=2026
TEACHER_NAME=admin
ADMIN_PASSWORD=SuperSecretPassword
```

## 🧩 Using `dotenv` to Load `.env` Files

For real projects, you use the `python-dotenv` package.

### Step 1: Install it

```bash
pip install python-dotenv
```

### Step 2: Create `.env`

```env
SCHOOL_TERM=spring
LOG_LEVEL=info
```

### Step 3: Load it in Python

```python
from dotenv import load_dotenv
import os

load_dotenv()  # Load from .env file automatically

print(os.getenv("SCHOOL_TERM"))  # Outputs: spring
print(os.getenv("LOG_LEVEL"))    # Outputs: info
```

> 🛡️ Recommended for local development, testing, and small scripts. For bigger, shared systems, set the variables directly in that system's environment instead of relying on a .env file.

## 📘 Types of Environment Variable Values

Environment variable values are **always strings**. You need to **cast** them if needed:

```python
# Get max students allowed as an int
max_students = int(os.environ.get("MAX_STUDENTS", 30))

# Convert bool
strict_grading = os.environ.get("STRICT_GRADING", "False").lower() in ("true", "1", "yes")
```

---

## 📦 os.environ – Methods and Properties

| Method/Usage               | Description                                  |
| -------------------------- | --------------------------------------------- |
| `os.environ.get(key)`      | Get value or None                            |
| `os.environ.get(key, def)` | Get value or default                         |
| `os.environ['key']`        | Direct get – throws KeyError if not found    |
| `os.environ['key'] = val`  | Set an env var temporarily                   |
| `del os.environ['key']`    | Delete an env var                            |
| `os.environ.copy()`        | Copy of all env vars – useful for subprocess |

## 🔒 Best Practices

* ✅ Never hardcode secrets into your code.
* ✅ Use `.env` files **only for local development**.
* ✅ Set environment variables directly wherever the program actually runs, for anything beyond local development.
* ✅ Convert string env vars to proper types.
* ✅ Validate required env vars at startup.
